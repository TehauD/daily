# The Daily: Test the Agent, Not the Demo

An agent can appear complete long before it is trustworthy. A polished response proves almost nothing unless the output is compared with an expected answer and the misses are captured systematically.

Today I moved a contract-focused Copilot Studio agent into user acceptance testing. The meaningful change was not simply giving testers access. It was defining what they should test and how their feedback would change the system.

## The theme: Evaluation needs an explicit contract

The testing guidance was intentionally simple. Upload a representative document, review the response, compare it with the approved standard, and record anything that was missed, misclassified, or unclear.

The initial evaluation scope focused on alignment with core provisions, identification of deviations and missing clauses, basic risk surfacing, and a consistent output structure. Those are bounded behaviors that a domain reviewer can inspect. They are stronger than asking whether the agent feels useful.

I made the current instructions visible as a starting point rather than treating the prompt as hidden implementation detail. That gave reviewers a way to connect an incorrect result to the behavior we had actually specified.

## Field notes from the build

Tester access was confirmed, and the premium Microsoft 365 license exposed broader Copilot functionality across the productivity suite. That expanded the tool surface, but it also increased the need to separate platform capability from this agent's acceptance criteria.

The feedback mechanism needed to support short observations. A reviewer should be able to say that the agent failed to flag governing law, assigned the wrong risk, or produced an unclear explanation. Those observations can become regression cases instead of disappearing into meeting notes.

A broader prompt workshop the same day reinforced the value of clear context, goals, source material, and expected output. It also surfaced practical differences between licensed experiences and occasional service constraints. Those were useful platform lessons, but they were not evidence that the contract agent itself had passed testing.

I also worked through an immature intake process for new AI requests. The lack of a formal enterprise route meant the platform path could be documented while the higher-level AI review still depended on people knowing where to carry the request. That is a governance risk because good technical work can move faster than the approval evidence around it.

A solution catalog effort added another evaluation challenge: metadata extraction should return controlled values, avoid inferring ambiguous dates, and distinguish visible metrics from generic fields. Constraints like those turn an open-ended model response into a testable interface.

## What moved

-

Implemented user acceptance testing guidance for a contract-focused Copilot Studio agent.

-

Confirmed tester access to the agent.

-

Defined bounded MVP behaviors for comparison, deviation detection, risk surfacing, and output consistency.

-

Established a lightweight feedback pattern that can become regression tests.

-

Advanced controlled-vocabulary rules for AI-assisted metadata extraction.

-

Documented a gap between platform intake and enterprise AI governance.

## The reusable pattern

Every agent should have an evaluation contract containing representative inputs, expected findings, allowed labels, prohibited assumptions, output schema, reviewer role, and acceptance threshold.

Store each reviewer correction as a versioned test case. Run the suite whenever instructions, knowledge, connectors, or models change. That creates an evidence trail from prompt revision to observed behavior.

The future state is continuous agent evaluation: feedback enters a structured queue, approved examples join the regression set, deployments run automated checks, and production telemetry identifies where new tests are needed.

## Standing takeaways

-

Access is a prerequisite, not acceptance.

-

Domain reviewers need observable criteria, not a general request for feedback.

-

Controlled outputs make model behavior easier to test and govern.
