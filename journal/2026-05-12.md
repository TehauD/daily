# The Daily: Human Authority Has to Be Part of the Architecture

The most useful AI prototype is not the one that tries to finish the whole job. It is the one that removes the repetitive first pass while making the human decision easier to inspect.

Today I demonstrated a contract analysis agent built in Microsoft Copilot Studio. The hard part was not showing that a model could compare documents or summarize clauses. The hard part was defining where automation should stop.

## The theme: Narrow the agent until it becomes trustworthy

Contract review is judgment-heavy, but much of the initial work is repetitive. A reviewer has to locate relevant sections, compare them with an approved template, identify deviations, and decide which differences deserve attention. An agent can accelerate that sequence, but it should not quietly become the authority.

I framed the agent as an analysis assistant rather than an approval system. It surfaces differences and potential risks earlier, while the legal reviewer keeps control of interpretation and disposition. That boundary matters more than the sophistication of the prompt.

The demonstration moved through three levels of maturity. A manual prompt showed that the core comparison task was possible, but also exposed inconsistency and repeated setup. A custom agent added durable instructions, model controls, and a defined knowledge source. The next step is not more features. It is controlled evaluation with real examples in a non-production environment.

## Field notes from the build

The manual workflow was useful as a baseline because it revealed the cost of ad hoc prompting. The user had to provide the reference material, the contract, and the comparison instructions each time. Even when the output was helpful, the process was too dependent on prompt quality and human memory to be reliably reusable.

Grounding the custom agent in an approved template changed the operating model. The reference document could be maintained in a governed content location, and the agent could use the current version without requiring a fresh upload for every review. That reduces friction, but it also creates a dependency on document ownership, update controls, and traceability.

I also showed a single-document upload experience. Simplifying the interaction was important. The user should not need to assemble a bundle of prompts and reference files just to start an analysis. The agent should already know its purpose, its approved source, and the structure of the response.

The largest unresolved design question is template breadth. One agent can be taught to recognize multiple agreement types, but expanding too quickly risks ambiguous routing and inconsistent comparisons. The better path is to start with one template, establish an evaluation set, and only add document types after the failure modes are understood.

Another open question is coexistence with an incoming commercial tool. A useful proof of concept does not justify duplicating a platform capability. The agent needs a clear role, either as a focused bridge, an evaluation benchmark, or a reusable pattern for workflows the larger tool will not cover.

## What moved

-

Demonstrated a custom contract analysis agent in Microsoft Copilot Studio.

-

Validated a simpler single-document review flow grounded in an approved reference template.

-

Established human review as the authority for legal interpretation and final decisions.

-

Defined an initial test scope around one contract template rather than broad document coverage.

-

Identified non-production evaluation as the next gate before any wider deployment.

## The reusable pattern

Start with the repetitive comparison task, not the final decision. Ground the agent in a controlled reference source. Make the user interaction smaller than the manual process. Route the output to a human reviewer with enough structure to verify the result.

Then evaluate against real examples before expanding scope. New templates should be treated like new model behaviors, with their own tests, expected outputs, and documented failure cases.

This pattern applies well beyond contracts. Policy review, standards mapping, technical intake, and structured document quality checks all benefit from the same architecture: narrow task, governed knowledge, inspectable output, human authority, and staged promotion.

## Standing takeaways

-

A strong agent removes setup work without removing accountable judgment.

-

Reusable instructions and governed knowledge matter more than an impressive one-time prompt.

-

One well-evaluated template is more valuable than broad but ambiguous coverage.

-

Deployment environments are part of the product design, not an administrative afterthought.

## Open thread

I need to turn the demonstration into an evaluation package with representative documents, expected findings, false-positive tracking, and explicit promotion criteria. I also need to define whether this agent complements or duplicates the larger legal technology roadmap.
