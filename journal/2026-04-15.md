# The Daily: A Prototype Needs a Governed Path to Testing

The difficult part of an agent project is rarely getting the first response. The difficult part is creating a path where the response can be evaluated, promoted, and trusted without bypassing the controls around it.

Today I worked across an AI adoption checkpoint, a Power Platform governance review, and an Azure deployment session. The throughline was environment separation. Development, testing, and production are not administrative labels. They are how uncertainty is contained.

## The theme: Separate experimentation from evidence

The contract analysis agent had reached the point where additional prompting alone would not create meaningful progress. It needed a place for controlled testing, access for domain reviewers, and a promotion model that could preserve the distinction between exploration and release.

I advanced the request for managed development and test environments, a dedicated security group, and an initial credit allocation. The intended model was explicit: solution changes move from development to test before production, and any custom connector or DLP exception returns to governance for review.

This is slower than building directly in a shared environment. It is also far more reusable. Once the path exists, future projects do not have to negotiate the same boundaries from scratch.

## Field notes from the build

The AI leadership discussion connected the technical prerequisites to the adoption program. The legal use case still needed licenses for domain reviewers and continued refinement against their workflow. Broader citizen development also remained an open design problem. Access has to be widened in a format that is governable, not simply enabled tenant-wide.

The governance review turned those needs into concrete environment work. Development and test were identified as the minimum initial setup for formal workflow testing and automated promotion. Production remained part of the target architecture, but it was not treated as the next immediate destination.

The group also required managed environments and explicit review of custom DLP configurations or new connectors. That draws an important line between baseline capabilities and project-specific exceptions. A new connector is not only a feature request. It is a change to the platform's data movement and authentication surface.

Later, I worked through a separate Azure deployment problem. Development and test resources were created alongside an existing production footprint. A shared virtual network and app service plan could be reused for non-production, which reduced unnecessary infrastructure duplication.

Manual provisioning was accepted for the one-time setup, even though infrastructure as code was discussed as an alternative. That was a pragmatic choice, but it leaves a reproducibility gap. Manual creation can be efficient once. It becomes expensive when the same environment must be rebuilt or audited.

The deployment pipeline also exposed unresolved technical issues. A function app required a managed identity authentication pattern that still needed investigation. The pipeline had an agent-pool parameter error that required review in the YAML and configuration. I did not treat the deployment as complete.

## What moved

-Advanced managed development and test environments for a contract analysis agent.

-Defined a dedicated security group and initial environment allocation as governance prerequisites.

-Established development-to-test-to-production as the intended promotion path.

-Confirmed that custom connectors and DLP exceptions require additional review.

-Created separate Azure development and test resources while preserving the production resources.

-Reused approved shared infrastructure for non-production where the design allowed it.

-Identified unresolved managed identity and pipeline configuration issues before deployment.

## The reusable pattern

Create the delivery path before scaling the feature set.

Provision separate stages. Bind each stage to the right security group and policy baseline. Keep environment-specific values out of application logic. Promote through source control and pipeline configuration. Require domain evaluation in test before production.

For one-time infrastructure work, manual provisioning can be acceptable when every resulting setting is captured. The better future state is a versioned environment manifest that can generate or validate the resources later.

## Standing takeaways

-Development and test are controls for uncertainty, not hosting preferences.

-Agent accuracy requires domain review, not only technical validation.

-Connector exceptions change the security boundary and deserve explicit approval.

-Reusing shared infrastructure can reduce complexity when isolation requirements are still met.

-A pipeline error found before production is evidence the staging model is working.

## Open thread

The remaining work is to resolve managed identity authentication, correct the pipeline agent-pool configuration, complete reviewer access, and define the evaluation evidence required for promotion.
