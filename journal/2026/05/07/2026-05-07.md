# The Daily: Governance Needs Evidence, Not Just Guardrails

A governance baseline can be perfectly written and still miss the risk users actually experience. Today the gap showed up in search quality: broad file sharing does not only increase exposure, it can also pollute the context an AI assistant retrieves.

I reviewed updates to a Power Platform baseline and worked through data loss prevention, developer accountability, connector controls, and oversharing. The key shift was moving from policy language to evidence that can be measured across the tenant.

## The theme: Permissions shape both security and AI quality

Traditional access reviews ask whether a user can open a file. AI changes the question. If a user can access thousands of marginally relevant or broadly shared artifacts, those files can enter retrieval results and weaken the assistant's answer even when no permission boundary is technically violated.

That makes oversharing both a security issue and a quality issue. The same permissive group that creates unnecessary access can introduce stale, duplicate, or misleading content into Copilot search. Fixing the problem requires more than reminding people to share carefully.

We reviewed a revised DLP strategy and discussed new controls that allow specific actions on otherwise approved connectors to be enabled or disabled. That granularity is useful because connector risk is not binary. A read action and a destructive write action should not inherit the same default simply because they come from the same connector.

## Field notes from the build

The baseline review exposed a second governance concern: cost responsibility. Agent activity can trigger consumption that is not obvious to the developer at design time. A technical platform needs a developer agreement that makes ownership, acceptable use, cost awareness, and compliance responsibilities explicit before an application or flow is released.

The oversharing discussion was grounded in direct examples of broad internal access degrading Copilot search results. That evidence changed the conversation. Instead of treating permissions hygiene as an abstract control, it became a visible product-quality problem.

The proposed technical response was a tenant-level permissions audit. The script would iterate through sites, identify broad sharing patterns, and produce a reviewable inventory. The goal is not to remove access automatically. It is to make the current state observable enough that owners can distinguish intentional collaboration from accumulated exposure.

A useful audit must preserve context. Broad access alone is a signal, not a verdict. The output should include the site, sharing principal, affected scope, ownership, last activity, and a classification that supports review. Public-facing output must remain generalized, but the internal remediation process needs enough precision to act.

The discussion also reinforced that governance documentation should be versioned. The baseline was being updated to reflect a new DLP strategy and prepared for a later publication. Versioning gives the team a way to explain which policy applied when a solution was built or approved.

## What moved

-Reviewed an updated Power Platform baseline aligned to a revised DLP strategy.

-Identified developer cost responsibility and acceptable-use expectations as missing governance requirements.

-Validated that broad internal sharing can degrade Copilot retrieval quality.

-Defined a tenant permissions audit as the next technical mechanism for finding overshared content.

-Explored action-level restrictions for approved connectors instead of relying only on connector-wide allow or block decisions.

## The reusable pattern

Turn policy concerns into measurable controls.

Start with a documented baseline. Add tenant scans that discover actual configuration and permissions. Route findings to owners for review. Track exceptions with rationale and expiration. Re-run the scan to verify remediation and detect drift.

For AI-enabled platforms, evaluate governance across three dimensions: access, action, and retrieval quality. Access asks who can reach the content. Action asks what the connector or agent can change. Retrieval quality asks whether the available content improves or degrades the answer.

The future state is continuous control monitoring. A scheduled audit can detect broad sharing, risky connector actions, unowned solutions, and policy drift, then produce a prioritized remediation queue instead of another static report.

## Standing takeaways

-Oversharing can reduce AI answer quality even when access is technically authorized.

-Connector governance should distinguish read, write, and destructive actions.

-Developer agreements need clear ownership for cost and compliance.

-A baseline becomes operational only when configuration can be measured against it.

## Open thread

I need to design the permissions audit so it identifies meaningful exposure without flooding reviewers with expected collaboration. The hardest part is not enumeration. It is producing a defensible signal that leads to action.
