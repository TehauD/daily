# The Daily: Prototype Before Platform

The first version did not need to solve the entire dataset. It needed to make the unknowns visible.

## The theme: Use the smallest useful surface

I had a working Power Apps prototype for a financial-adjustment workflow. The app was explicitly in a development state so stakeholders could inspect the available fields and decide what needed to be displayed and maintained when creating records.

The largest constraint was scale. The available source contained hundreds of thousands of records, which pushed the design toward premium SQL connectivity. I challenged whether the first workflow truly needed every historical record or whether a smaller active subset could support the immediate use case.

## Field notes from the build

The prototype gave the team something concrete to react to without pretending the requirements were complete. A development interface was enough to test field selection, entry expectations, and the practical implications of source volume.

I also helped troubleshoot access to an external analytics API and confirmed the connection worked. That unblocked a separate proof of concept, but the day's evidence did not yet show a production integration.

Another useful thread involved SharePoint governance automation. I shared a PnP PowerShell connection pattern and reviewed a tenant-scanning script intended to locate broad access assignments. The script was still being shaped, so I treated it as implementation support rather than a completed control. #type/win

A team code review provided direct learning about domain identifiers and financial containers. The practical takeaway was that similar-looking identifiers represent different grains. A stable person identifier, an encounter identifier, and a financial account identifier should never be treated as interchangeable keys.

Automated batch messages reported successful executions with row-count differences. Those alerts remained supporting context only. They reinforced why a green status should not be interpreted as data equivalence.

## What moved

-Demonstrated a functional Power Apps prototype in a development environment.

-Defined the next requirement questions around displayed fields and editable attributes.

-Identified source volume and connector licensing as architectural constraints.

-Validated access to an external analytics API for a separate proof of concept.

-Shared a reusable PnP PowerShell connection pattern for SharePoint governance work.

-Advanced my understanding of identifier grain through a transcribed code review.

## The reusable pattern

Build the smallest surface that exposes the real decisions. Keep the first version narrow, instrument its constraints, and use stakeholder interaction to turn assumptions into requirements.

For data-heavy apps, profile row volume, key grain, update behavior, and access requirements before selecting the connector or storage tier.

## Standing takeaways

-A prototype should expose unknowns, not hide them.

-Data volume can change both architecture and licensing.

-Similar identifiers can represent entirely different grains.

## Open thread

The workflow still needed a confirmed record scope, final field set, and production-grade data path.
