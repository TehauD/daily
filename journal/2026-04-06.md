# The Daily: Anomalies Need Context Before They Need More Intelligence

An anomaly detector can be technically correct and still create more work than it removes. The hard part is not finding unusual behavior. It is deciding which deviations deserve an engineer's attention.

Today I documented the current state of a network anomaly workflow built around Python-based API pulls, learned baselines, and a custom interface. The strongest lesson was that operational usefulness depends on context, pacing, and human interpretation more than model novelty. #type/learning

## The theme: Detection without prioritization becomes alert fatigue

Static thresholds are attractive because they are easy to explain. They are also brittle when infrastructure behaves differently by site, time window, or operating condition.

The approach under review used adaptive baselines instead. The system compared observed behavior with learned local norms and returned explicit anomaly lists with scores indicating the degree of deviation. Engineers retained control over interpretation and remediation.

That boundary was important. The workflow was decision support, not autonomous operations. If the detector failed, network services did not directly change. A human still determined whether an anomaly represented a real issue and what action was appropriate.

## Field notes from the build

The current implementation pulled data internally from wireless controllers through Python. API usage was intentionally throttled to avoid straining the source systems. Batch or near-real-time processing was discussed as the practical balance between freshness and load.

This introduced an architectural tradeoff. Faster polling can improve detection latency, but it also increases data volume, compute cost, and pressure on operational APIs. The right interval should be based on the response window the engineering team actually needs, not on the fastest schedule the platform can support.

The evaluation plan was still immature. Traditional machine learning metrics had not yet been defined or reported. Current evaluation focused on whether surfaced anomalies were relevant and whether the workflow reduced manual troubleshooting effort. Those are useful operational signals, but they do not replace a labeled evaluation set.

Storage was another limitation. JSON-only output supported the current interface but did not provide the centralized history needed for trend analysis. Integration with a database, Grafana, or another centralized platform was discussed as a next step rather than an implemented capability.

The risk review identified false positives, alert fatigue, scalability, compute cost, and missed anomalies. The mitigation direction was consistent: learn per-site and per-time-window norms, filter unnecessary data at ingestion, pace processing, and consider lower-cost non-AI methods where they are sufficient.

That last point matters. An AI label does not make a detector better. If a simpler statistical method catches the same operational condition with lower cost and clearer behavior, it may be the more production-ready choice.

## What moved

-

Documented the current Python-based anomaly detection workflow and its data path.

-

Established adaptive, local baselines as preferable to one-size-fits-all static thresholds.

-

Clarified that engineers retain interpretive and remediation authority.

-

Identified centralized storage as a prerequisite for trend analysis.

-

Captured false positives, alert fatigue, scalability, compute cost, and missed anomalies as explicit risks.

-

Defined ingestion filtering and paced processing as practical mitigation strategies.

## The reusable pattern

Build operational anomaly detection as a decision-support pipeline.

Collect only the signals needed. Normalize behavior by relevant context. Score deviations. Store results centrally. Present the reasoning in a form an engineer can inspect. Track whether alerts lead to useful investigation.

Evaluation should include labeled examples, precision, recall, alert volume, time-to-triage, and cost per processing window. The release gate should focus on usefulness at the operating threshold, not peak offline accuracy.

The future state is continuous calibration. Confirmed incidents and dismissed alerts can feed an evaluation store, allowing thresholds and baselines to be reviewed without turning production behavior into uncontrolled retraining.

## Standing takeaways

-

An anomaly score is evidence, not a decision.

-

Local baselines are safer than universal thresholds in variable environments.

-

Polling frequency should follow the operational response requirement.

-

Central history is required for trend analysis and measurable improvement.

-

Simpler methods should remain in scope when they meet the need.

## Open thread

The next step is to define a labeled evaluation set and a centralized result schema so operational usefulness, false positives, latency, and cost can be measured together.
