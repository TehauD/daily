# The Daily: Evaluate the Behavior, Not the Demo

The agent improved from a rough first pass to a much stronger result, but the failures became more instructive than the score. It could combine context impressively and still merge two separate conversations into a false conclusion.

That is the danger zone for enterprise assistants. Fluency can hide a broken evidence boundary.

## The theme: Move from prompt tuning to probabilistic evaluation

I reorganized the assistant around explicit core instructions, constitutional constraints, boundaries, persona, routing, and modular skills. The measured result improved from 58 percent to 83 percent in the available evaluation workflow. That showed the structure was helping, but it did not prove reliability.

The most valuable failure involved a significant inference that connected unrelated conversations. The result was coherent and wrong. That shifted the evaluation question from whether an answer sounds useful to whether the model consistently preserves source identity, temporal boundaries, and uncertainty.

I discussed evaluating these systems probabilistically, using concepts such as agreement and standard predictive metrics as inspiration. The exact method remains open, but the direction is clear. Agent quality needs repeated trials, labeled expectations, and failure categories. A single scripted demo cannot establish trust.

## Field notes from the build

The modular agent contained multiple domain skills for architecture, AI engineering, automation, data engineering, product strategy, prototyping, modernization, platform navigation, implementation, DevOps, and technical writing. Framework files separated core behavior from routing and boundaries. This made the system easier to reason about than one large instruction block.

I also explored a Microsoft research project that treats natural-language skills as trainable artifacts improved through feedback and validation loops. The pattern aligned with the direction I was already taking: version skills, evaluate them, and preserve changes in source control. I treated this as an explored design influence, not a production capability claim.

The day also advanced the builder pathway. Several users were granted access to a shared pilot environment and confirmed that access. The model was intentional: build in a sandbox, establish proof of value and risk, then move through formal governance before a dedicated environment is created.

A licensing discussion added an important process correction. If consumption credits require departmental funding, purchasing and chargeback need to occur before provisioning. Adding that gate early prevents a successful prototype from becoming an unfunded operating commitment.

## What moved

-

Implemented a modular agent architecture with explicit core, constitution, boundary, routing, persona, and skill components.

-

Improved the available evaluation result from 58 percent to 83 percent.

-

Identified cross-conversation inference as a concrete reliability failure mode.

-

Validated pilot-environment access for new builders.

-

Added licensing and chargeback as a pre-provisioning requirement in the emerging governance process.

-

Explored versioned, feedback-driven skill optimization as a future architecture pattern.

## The reusable pattern

Build an evaluation harness around labeled prompts, repeated runs, expected evidence, prohibited inferences, and failure taxonomies. Store every prompt, model configuration, response, score, and reviewer decision as a versioned test artifact.

For agent skills, use the same loop as code: propose a change, run regression tests, compare behavior, require review, and promote only when the change improves the intended metric without creating a new safety failure.

## Standing takeaways

-

Better scores do not erase dangerous failure modes.

-

Source separation should be an explicit evaluation dimension.

-

Licensing belongs in the architecture decision record.

## Open thread

I still need a defensible reliability metric that captures consistency across repeated runs and penalizes unsupported synthesis more heavily than harmless formatting variation.
