# The Daily: Governance Is Model Infrastructure

A machine learning standard is useful only when it can answer operational questions. Which data trained this model? Which extract produced a feature? What changed since the last review? When does retraining require a new approval?

I finished the week by advancing a working machine learning governance standard around those questions. The document was still a work in progress, but it made the expected evidence concrete. #type/win

## The theme: Make lineage and review executable

The standard required training data to be referenced through versioned, immutable data assets or governed tables rather than ad hoc local files. It also required end-to-end lineage from source tables and extract dates through curated layers, features, and model inputs.

That requirement is more than documentation hygiene. It is what makes a result reproducible, a defect traceable, and a model review meaningful. If a feature cannot be connected to its source and extraction context, the organization cannot confidently explain why the model behaved as it did.

The supporting peer-review work also distinguished changes that could be logged from changes that should trigger fresh review. Routine retraining on data of the same shape and source could be pre-authorized when performance stayed within evaluated bounds. Changes to features, data sources, extraction definitions, algorithms, intended use, audience, or risk tier required renewed scrutiny.

## Field notes from the build

The standard connected governance to real platform objects. Versioning needed to live in the data and model systems, not in filenames alone. Lineage needed to be queryable. References needed access dates because cloud documentation and product names change.

This was also a reminder that governance should define interfaces instead of prescribing one giant platform. A team might use Azure Machine Learning data assets or governed lakehouse tables, but the invariant is the same: immutable versions, traceable lineage, reproducible inputs, and review evidence.

The week's application work reinforced the point. A team wanted to transfer low-code applications to a future support function, but the necessary platform roles and support capacity were not yet fully available. A technically correct solution without an operating owner becomes a delayed incident.

I also continued shaping a data-entry application against incomplete historical records. The next increment narrowed the first section to minimum viable attributes. That was progress in the interface, but not resolution of the data-quality risk. I kept those statuses separate.

A discussion about bias in AI-enabled hiring systems added another governance dimension. Model quality cannot be reduced to aggregate accuracy. Intended use, affected populations, review thresholds, and the consequences of error belong in the control model from the beginning.

## What moved

-

Advanced a working machine learning governance standard with versioning and lineage requirements.

-

Defined traceability from source and extract through features and model inputs.

-

Established a risk-based distinction between logged retraining and changes requiring fresh peer review.

-

Preserved an unresolved support-model gap for low-code applications.

-

Narrowed an application data table toward minimum viable attributes without overstating source-data completeness.

-

Incorporated intended use and bias risk into the broader evaluation lens.

## The reusable pattern

Represent every model release as an evidence bundle. Include immutable data references, code and environment versions, feature definitions, evaluation results, intended use, risk tier, approvals, and deployment metadata.

Then make re-review event-driven. A changed feature contract, new source, drift threshold breach, altered audience, or model revision should automatically open the appropriate review workflow. Non-behavioral changes can be logged and verified without forcing the full process.

This is governance as infrastructure: controls that follow the model through its lifecycle rather than a document reviewed once at the beginning.

## Standing takeaways

-

Lineage must be queryable, not merely described.

-

Retraining and redesign are different change classes.

-

A support owner is part of production readiness.

## Open thread

The standard still needed validation against real projects and an automated evidence model that teams could adopt without duplicating work.
