# The Daily: Reporting Starts with Stable Data, Not a Dashboard

A dashboard request often sounds like a visualization problem. Today it became clear that the durable work was underneath: stable schemas, reliable feeds, defined ownership, and reporting views that can survive changes in the source systems.

I joined a reporting discussion for a large integration program. The group identified three initial reporting needs: project status, financial integration, and executive tracking of risks, issues, decisions, and actions.

## The theme: Stabilize the interface before polishing the output

Each reporting need depended on a different source and ownership path.

Project status reporting needed a fixed filtered view that could be embedded on each project homepage. Financial reporting needed data from planning and financial systems plus additional business clarification. Executive tracking depended on SharePoint lists whose schemas were still changing.

That last dependency mattered. Building a polished dashboard before the source schema stabilizes creates rework and weakens trust. The work should be prioritized after the data contract is sufficiently stable.

## Field notes from the build

The meeting notes assigned formal requests for the three reporting areas. This established demand, but it did not mean the reports were delivered. #type/win

The technical discussion focused on data movement. Existing OData feed issues needed to be addressed, and the data management team needed to support movement of planning and SharePoint data into the warehouse. Centralizing the data would make the reporting layer less dependent on fragile direct connections.

A recurring short touchpoint was proposed to review and prioritize requests. That is a simple but useful operating pattern. Reporting backlogs become difficult when every stakeholder assumes their view is the primary product. A small recurring forum can keep scope, dependencies, and sequencing visible.

The week also included a direct email stating that much of the backend SharePoint logic was ready and that the next phase could involve dashboards and current-state analysis. I treated this as supporting evidence that the reporting conversation followed completed backend preparation, not as proof that the dashboards themselves were built. #type/win

The architecture should separate source capture, integration, semantic definition, and presentation. SharePoint can remain the operational interface while the warehouse provides history and cross-source reporting. The dashboard should consume a stable reporting model rather than reproduce source-specific business logic.

There is also a governance concern. Risks, decisions, and actions can include sensitive detail. Executive reporting should expose the minimum fields needed for oversight and preserve item-level access rules where necessary.

## What moved

-

Defined initial reporting needs for project status, financial integration, and executive work tracking.

-

Identified fixed filtered views as the requirement for embedding project status on project homepages.

-

Documented OData feed issues and warehouse integration as dependencies.

-

Established that changing SharePoint schemas should stabilize before dashboard development is prioritized.

-

Proposed a recurring prioritization touchpoint for reporting requests and progress.

-

Clarified the need for finance and data-management participation in source definition and integration.

## The reusable pattern

Design reporting from the data contract outward.

Identify the system of record, owner, refresh path, grain, keys, history requirements, and access boundary. Land the data in a governed reporting layer when cross-source analysis or history is required. Build the semantic model once. Let embedded views and dashboards consume that shared model.

The future state is metadata-driven reporting. Source schema changes should trigger automated compatibility checks, lineage updates, and a clear release decision before downstream datasets refresh.

## Standing takeaways

-

A dashboard is downstream of ownership and data quality.

-

Direct feeds are convenient but can create fragile operational dependencies.

-

Changing list schemas should not be hidden behind presentation work.

-

A shared reporting model reduces duplicated business logic.

-

Prioritization needs a recurring forum and explicit dependencies.

## Open thread

The next step is to define the source contracts, resolve the feed path, stabilize the operational list schemas, and establish acceptance criteria for each reporting product.
