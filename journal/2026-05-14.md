# The Daily: The Default Is the Real Security Boundary

A platform can have dozens of security controls and still be unsafe if the default path is too permissive. Today was about reducing the amount of trust required from every future maker.

I worked through a Power Platform and Copilot Studio baseline review, including connector exposure, tenant isolation, agent permissions, authentication context, and deployment controls. The strongest lesson was simple: advanced capability should be available by request, not silently included in the baseline. #type/learning

## The theme: Secure the common path before scaling the platform

Connector policy is easy to discuss as an allow-or-block decision. In practice, the risk depends on what the connector can access, whether it preserves the user's identity, whether it can write data, and whether it crosses a trust boundary.

I proposed removing advanced data and search connectors from the default baseline. They may be valuable, but they represent development-scale behavior and broader data movement. Requiring an explicit request creates a point where purpose, scope, ownership, and safeguards can be documented.

That choice creates more work for platform administration. I accepted that tradeoff because convenience at provisioning time can become ambiguity during an incident. The default should support common low-risk scenarios. Elevated capabilities should leave an intentional trail.

## Field notes from the build

We tested agent role behavior rather than relying only on labels in the administration interface. End-user access could be granted, while editor and transcript-oriented roles remained restricted without the required environment privileges. That was an important validation. The effective control was tighter than the initial discussion assumed.

The test reinforced a broader rule: permission design should be verified through actual role transitions. Documentation and control names can suggest a boundary, but only a representative access test confirms what a user can do.

Tenant isolation emerged as a practical control for preventing Power Platform connectors from moving data across tenant boundaries. The group agreed it was a strong security improvement, while still recognizing that existing integrations must be considered before enforcement.

Agent sharing was less settled. Sharing to broad groups is manageable when an agent only uses delegated user access. It becomes more consequential when an agent holds application-level rights or invokes a custom connector backed by a token, secret, or service identity. The sharing model needs to reflect the authentication model.

I also set up the first deployment pipeline for an agent and connected the initial commit to source control. The target was a staged move into a test environment where domain reviewers could evaluate accuracy. That work linked two concerns that are often separated: secure platform governance and repeatable application delivery.

A pipeline does not make an agent safe by itself. It does make changes visible, environments distinct, and promotion repeatable. Those properties create the foundation for testing, rollback, and approval gates.

The authentication discussion exposed a useful dividing line. Delegated connections typically constrain the agent to the user's permissions. Custom APIs and application identities can exceed that boundary. They are not automatically wrong, but they need stronger review, narrower permissions, and more deliberate sharing controls.

## What moved

-

Advanced connectors were removed from the proposed default baseline and shifted toward explicit approval.

-

Tenant isolation was selected as a security control worth enabling.

-

Agent access roles were tested and validated against actual permission behavior.

-

Risks around broad agent sharing and application-level identities were documented.

-

The first agent deployment pipeline was implemented with source control as the starting point.

-

A staged evaluation path was established through a non-production environment.

## The reusable pattern

Define a low-risk baseline, then make exceptions explicit. Separate connectors by capability, data movement, write access, and authentication context. Test permissions with representative users. Keep development, test, and production distinct. Promote through source control and a repeatable pipeline.

For agent platforms, add one more layer: pair the sharing policy with the identity model. A broadly shared agent using delegated access is not equivalent to a broadly shared agent holding application permissions.

The future state is policy-driven provisioning. Environment creation, connector assignment, security groups, deployment pipelines, logging, and evaluation gates should be generated from a versioned configuration instead of assembled manually.

## Standing takeaways

-

Defaults scale faster than documentation, so defaults deserve the strongest design attention.

-

Advanced connectors should require an explicit purpose and owner.

-

Permission labels are not evidence. Test the actual access path.

-

Source control and environment promotion are governance controls as well as engineering practices.

-

Agent sharing cannot be evaluated separately from connector authentication.

## Open thread

The remaining work is to test third-party connector authentication, decide how group sharing should change for agents with elevated rights, and convert the baseline decisions into a versioned, repeatable provisioning standard.
