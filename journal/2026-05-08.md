# The Daily: A Correct Model Can Still Be the Wrong System

Accuracy is an incomplete definition of success. A model can return the correct answer and still be too slow, too expensive, too opaque, or too brittle to use.

Today I studied evaluation patterns for AI and machine learning systems, with a focus on functional correctness, efficiency, continual learning, experiment tracking, and production validation. The throughline was that evaluation has to follow the system, not stop at the model output. #type/experiment

## The theme: Evaluate what users and operators actually experience

For code, SQL, and tool-using agents, functional correctness is necessary. It is not sufficient. A generated query can return the right result while consuming unreasonable memory or taking too long to run. An agent can select a valid tool but pass the wrong parameters. A plan can look coherent but violate the user's constraints.

These are different failure classes and they need different tests. Treating them as one accuracy score hides where the system actually breaks.

The same applies after deployment. A stationary test set cannot explain how a model behaves when live data changes. Continual learning is largely an infrastructure problem because retraining, validation, rollout, observation, and rollback must all work together.

## Field notes from the build

I reviewed examples of planning failures in tool-using agents. One failure mode is structural: the agent chooses a tool that exists but calls it with an invalid parameter shape. Another is semantic: the parameter schema is valid, but the value is wrong. A third is goal failure, where the plan does not satisfy the task or ignores a constraint.

That taxonomy is immediately reusable. Schema validation can catch structural failures before execution. Reference cases can test semantic argument selection. End-to-end task assertions can determine whether the final goal and constraints were met.

I also focused on efficiency as an evaluation dimension. Functional correctness should be paired with runtime, memory, token use, or execution cost where those qualities affect usability. The ground truth is not only the expected answer. It can also include an expected performance envelope.

Experiment tracking provides the bridge between isolated results and engineering understanding. Capturing code, configuration, inputs, outputs, metrics, and timestamps makes it possible to compare changes and debug regressions. Tracking everything is tempting, but indiscriminate telemetry can bury the signals that matter. The instrumentation plan should start from failure modes and operational decisions. #type/experiment

Production testing introduces a harder constraint. Live validation is necessary when data distributions shift, but it cannot be reckless. Safer patterns include limited exposure, shadow execution, explicit health checks, rollback criteria, and comparison against the current system. The goal is to learn from production conditions without turning users into an uncontrolled experiment. #type/experiment

A canceled working session left less direct build evidence for the day, so I am treating this as an exploration and design day rather than claiming implementation. The concrete outcome was a clearer evaluation model that can be applied to future agent and ML work.

## What moved

-Explored a failure taxonomy for tool selection, parameter validity, parameter correctness, and goal completion.

-Defined efficiency and cost as first-class evaluation dimensions alongside correctness.

-Connected continual learning requirements to deployment, monitoring, and rollback infrastructure.

-Identified experiment tracking as the mechanism for comparing changes and investigating regressions. #type/experiment

-Clarified safer patterns for validating models under production data conditions.

## The reusable pattern

Build evaluation as a layered contract.

Validate schemas before execution. Test semantic arguments against labeled cases. Assert end-to-end goals and constraints. Measure runtime and cost. Capture experiment lineage. Monitor live behavior for distribution change. Release through controlled exposure with explicit rollback thresholds. #type/experiment

This converts evaluation from a scorecard into an operating system for improvement. Every failure should map to a test, every test to a release gate, and every production signal to a decision the team is prepared to make.

## Standing takeaways

-Correct output does not compensate for unacceptable runtime or cost.

-Agent evaluation should separate tool, argument, and goal failures.

-Continual learning depends more on infrastructure than on retraining code.

-Telemetry is useful when it supports a defined operational decision.

-Production validation requires controlled exposure and rollback, not optimism.
