# The Daily: Find the Actual System Boundary

A workflow can look like a form problem when the real issue is that information is being copied between systems without a clear owner.

Today I worked through a contract intake flow and compared the details captured in a request form with a separate checklist. The overlap raised a basic architecture question: is one artifact authoritative, or is someone manually transposing the same information from one place to another?

## The theme: Duplicate capture usually signals a missing boundary

The discussion exposed a familiar tension between buying a vendor solution and building an internal one. That decision is easy to frame as a feature comparison. It is more useful to begin with the flow of information.

If two tools collect nearly the same detail, adding another form does not improve the process. It creates another state to reconcile. Before choosing a platform, I need to know where the request originates, which system owns each field, who is allowed to update it, and what event advances the work.

The evidence supported exploration and problem framing. It did not establish that a new integration or application was implemented that day.

## Field notes from the build

The request form and checklist appeared to contain substantially similar information. That suggested the process may include re-entry, submission on another person's behalf, or a handoff between teams that is not represented as a system event.

Each possibility leads to a different design.

If the issue is re-entry, the strongest pattern is to capture the data once and pass a stable identifier downstream. If the issue is delegated submission, the model needs both the requester and the submitter. If the issue is a review checklist, the checklist should reference the original request rather than duplicate its attributes.

The buy-versus-build question remains important, but it should follow the boundary analysis. A vendor product may offer mature workflow controls, while an internal solution may fit existing identity and data patterns more closely. Neither option is automatically better if the authoritative record remains ambiguous.

I also need to be careful with the evidence level. The chat documented questions and architectural tension, not a completed design. I am calling this explored work because the useful outcome was a sharper problem definition. #type/win

## What moved

-

Compared overlapping contract intake artifacts.

-

Identified potential manual transcription between systems as a design risk.

-

Framed the vendor-versus-internal decision around data ownership and workflow boundaries.

-

Distinguished delegated submission, duplicate entry, and review activity as separate requirements.

## The reusable pattern

Map the record before selecting the tool.

For each field, define the system of record, creator, editor, reviewer, and downstream consumers. Represent handoffs as events. Preserve the original identifier across every step. Generate checklists and views from the authoritative record rather than copying its content.

The future state is a contract intake event that creates one governed record, routes review tasks, and publishes status without requiring people to transpose the same details between interfaces.

## Standing takeaways

-

Similar forms often reveal duplicate state rather than missing functionality.

-

Buy versus build should follow a clear data ownership decision.

-

Delegated submission requires explicit identity fields.

-

A checklist should validate the source record, not become another source.

-

Exploration is valuable when it reduces ambiguity before implementation.

## Open thread

The next step is to document the current-state handoffs and determine whether the duplicate artifacts serve distinct control purposes or represent avoidable re-entry.
