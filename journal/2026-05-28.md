# The Daily: Turn Intake Into an Interface

A comprehensive intake form can still be a bad interface. Today the process became more useful when I separated what requestors know from what governance must decide.

## The theme: Ask each role only what it can answer

I reviewed the emerging Copilot Studio intake process with the platform group and with an early requestor. The draft had accumulated more than a hundred lines covering business justification, risk, environments, connectors, roles, licensing, and operational controls.

The breadth was useful for governance, but it was too much for a person describing a use case. Direct feedback identified the right split: requestors should provide the problem, value, audience, data sensitivity, access needs, expected scale, and sponsorship. Governance should translate that into environments, groups, policies, connectors, roles, and approval routing.

## Field notes from the build

The baseline review also surfaced workload design. Several project environments were expected, each potentially requiring development, test, and production stages. I asked whether provisioning should be handled in batches or incrementally and checked that the implementation workload was manageable.

That conversation led naturally toward automation. Repeating the same environment setup many times is a signal that the process should become a parameterized script or pipeline. Before automating it, I wanted the end-to-end procedure documented and the intake fields stable.

The same day exposed two useful technical failures. A Power BI application displaying stale-year data was removed and reinstalled, after which refreshed data became visible. The initial refresh had no convenient status page and could take an unpredictable amount of time, which made observability part of the support problem.

A separate Azure DevOps deployment failed with a bad archive after environment approvals were corrected. I did not mark the application deployed. The pipeline and approval path were implemented, but the build artifact still needed correction.

For the legal agent, I restored visibility after a configuration had been inadvertently flipped. Reviewers confirmed the agent appeared again. Additional licenses were still pending for other testers.

## What moved

-

Refined the AI intake process through platform and requestor feedback.

-

Identified a clean boundary between requestor inputs and governance-owned configuration.

-

Advanced planning for repeated environment provisioning and automation.

-

Restored test-agent visibility after correcting an access configuration.

-

Validated refreshed Power BI data after an application reinstall.

-

Advanced an Azure DevOps pipeline through approvals, while preserving the failed archive as unresolved.

## The reusable pattern

Use a two-stage intake. Stage one captures intent in plain language. Stage two converts intent into an architecture and control plan through deterministic rules and governance review.

The automation opportunity is a request compiler. A validated intake record should generate names, security groups, environment definitions, policy assignments, approval tasks, and a provisioning plan without making the requestor understand the platform internals.

## Standing takeaways

-

Comprehensive does not mean usable.

-

Governance configuration should be derived from intent where possible.

-

Provisioning automation should follow a stable, documented contract.

## Open thread

The process still needed a smaller requestor-facing form and an idempotent provisioning implementation.
