# The Daily: Design for Change Before Loading Data

The load was not the hard part. The harder question was what should happen when the source changes after the first successful run.

I spent the day moving a SharePoint-to-Synapse pipeline from a one-time copy toward change-aware behavior. The work exposed the decisions that determine whether a pipeline remains reliable after launch: schema placement, naming, staging behavior, key selection, updates, deletions, and ownership of future changes.

## The theme: Idempotence starts with the data contract

In a transcribed working session, I corrected a schema that had been provisioned in the wrong location and recreated the required tables using established staging conventions. I then worked through pipeline configuration and publishing with a focus on repeatable loads.

The staging pattern was straightforward. Truncate before reload so repeated executions do not accumulate duplicates. The final-table pattern required more thought. The working key was a composite of invoice number and line number, but we left the final decision open pending additional analysis and confirmation of how the source is edited or deleted.

That distinction matters. An upsert is safe only when the key represents the business record consistently. A technically unique combination that changes over time can silently convert updates into inserts.

## Field notes from the build

The pipeline used a raw staging table followed by an upsert into the final table. The working guidance was to preserve source values in staging, align final data types with the SharePoint source, and use the composite key for matching once the required columns were present.

A float-type issue on identifier-like fields reinforced the need to inspect how connectors infer types. Values that behave as identifiers should not inherit a numeric representation simply because they contain digits. The available evidence shows the issue was investigated and the rest of the fields appeared acceptable. It does not establish a final production fix.

I also documented an unresolved policy dependency. The change-data-capture design depends on whether source records can be edited or deleted. That question was deferred to a future business review, so I did not encode deletion behavior as a settled requirement.

Outside the pipeline, I shared a leadership status update covering completed connector enablement, an environment provisioning guide in progress, intake and approval work, and an upcoming legal-assistant test. I also contributed two reusable team patterns: a stricter Azure DevOps branch-control approach and a transcript-to-chapter workflow after automatic chapters did not generate as expected. #type/win

## What moved

-Corrected the target schema location and recreated staging-aligned structures.

-Configured and published a repeatable staging and upsert pipeline pattern.

-Implemented truncate-before-load behavior for the staging table.

-Explored a composite business key for deduplication and updates.

-Documented open dependencies around record edits, deletions, and final key selection.

-Shared reusable branch-control and transcript-chapter automation patterns.

## The reusable pattern

Separate ingestion into raw landing, typed staging, and curated final layers. Make each run restartable. Capture the source key, ingestion timestamp, source-modified timestamp, and operation type when available.

Before production, validate the key against duplicates, late updates, null values, and source corrections. Treat deletion handling as an explicit business rule, not an implementation guess.

## Standing takeaways

-A successful first load says little about the second run.

-Schema placement and naming are operational controls.

-Identifier fields should not be modeled by appearance alone.

## Open thread

The pipeline still needs a confirmed business key and an approved rule for source edits and deletions.
