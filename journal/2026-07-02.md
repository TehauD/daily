# The Daily: Access Is a Chain

A user could open the SharePoint list but could not create an item or populate its lookup fields. The first permission change fixed one symptom, then exposed the next dependency.

That was the useful lesson. Access is rarely one switch. It is a chain across the primary application, supporting lists, security groups, and the operations that keep those relationships current.

## The theme: Diagnose access from the user action backward

I worked through an access problem in a SharePoint-based workflow. The user initially could not see the control needed to add records. I updated the list permissions to allow item creation and editing, then asked for direct validation.

The next test showed that the user could reach the form but the dropdowns had no values and free-text entry was not allowed. That narrowed the issue to supporting lookup data rather than the main list alone.

I traced the missing behavior to a security group that automatically grants access to the supported lookup lists. I requested confirmation that the user had been included in that group, and the responsible team initiated the access request.

Nothing about this was technically exotic. The value came from following the user journey instead of declaring success after the first permission change.

## Field notes from the build

The initial adjustment changed the user's ability to create and update items in the primary SharePoint list. That was implemented, but it did not complete the workflow.

The second failure was more informative. Empty dropdowns indicated that the form was retrieving choices from another controlled source. Because the fields did not permit arbitrary text, missing read access to those sources made the form unusable even though the main list itself was available.

The access model depended on a security group that provided permissions to the related lookup lists. I escalated that specific dependency instead of broadening permissions across the site. The available evidence shows that the access request was initiated. It does not confirm that the user later completed the entire workflow, so I am not marking end-to-end access as validated. #type/win

A separate reporting validation thread recorded that two previously identified issues had been addressed and returned for additional testing. The evidence supports that updates were made available for validation, but not that every metric discrepancy was resolved. I am keeping that effort in the validated-in-progress category rather than calling it shipped. #type/win

Automated data-platform messages also reported successful jobs with row-count mismatches and a failed terminology batch. Those notifications are supporting context only. I did not treat receiving them as work completed. They reinforce the same principle: a top-level status can look healthy while a required dependency underneath it is not. #type/win

## What moved

-

Implemented create and update permissions for a user in a SharePoint-based workflow.

-

Diagnosed empty lookup controls as a separate access dependency from the main list.

-

Narrowed the missing access to a security group that grants permissions to supporting lookup lists.

-

Initiated the appropriate group-access request through the responsible team.

-

Advanced a reporting update into additional user validation without overstating unresolved metric differences.

## The reusable pattern

Model access as a dependency graph. Start with the intended user action, then enumerate the application, primary data store, lookup sources, groups, licenses, and downstream services required to complete it.

A reusable preflight check should test each dependency with the same identity before the user receives a link. For a SharePoint and Power Apps workflow, that means validating page access, list permissions, lookup reads, create and update operations, and any group-driven inheritance separately.

The future state is a small diagnostic tool that accepts a user and workflow, evaluates the permission graph, and returns the first broken dependency with an accountable remediation path. That turns access troubleshooting from email archaeology into a repeatable control.

## Standing takeaways

-

Opening the application is not the same as completing the workflow.

-

Lookup fields introduce data-source permissions that are easy to miss.

-

The narrowest correct permission is better than broad site access.

## Open thread

The remaining evidence gap is end-to-end confirmation that the group update restored the lookup values and allowed the user to submit a record successfully.
