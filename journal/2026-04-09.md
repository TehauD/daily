# The Daily: Capacity Is a Governance Control

An AI feature can look inexpensive while it is idle and become costly once a maker connects it to a document-heavy workflow. Without timely usage visibility, the platform team discovers the design problem after credits have already been consumed.

Today I worked through AI Builder and Copilot credit risks in the Power Platform baseline. The discussion moved from general concern to specific controls around environment creation, non-production usage, reporting, and user transition.

## The theme: Consumption needs boundaries before adoption scales

The platform did not have sufficient real-time monitoring for credit use. End users could consume significant capacity without understanding the cost model, and the existing tools were not considered adequate for proactive control.

The decision was to use administrator-generated development and sandbox environments, block AI Builder credits in non-production, and contact current high-consumption users about alternative licensing or solution patterns. The group also planned to submit a tenant-setting change for credit assignment. #type/decision

These are restrictive defaults, but they create a clearer operating model. Non-production should support safe experimentation without becoming an unbounded consumption surface.

## Field notes from the build

The first challenge was observability. Usage logs needed to be pulled and object identifiers matched to actual users before outreach could be targeted. This is a common governance pattern: the control plane exposes identifiers, while remediation requires a reliable mapping to accountable owners.

The second challenge was substitution. Blocking credits does not remove the underlying business need. The team discussed moving some users to a Copilot license or another approach and finding more cost-effective document-processing alternatives.

I also shared progress on a legal contract proof of concept using custom agents to compare documents against a controlled source of truth and a structured list of terms. That work made the credit question concrete. Document analysis can scale consumption quickly, so platform design and evaluation cost need to be considered together.

Environment creation was another open issue. Unexpected environment growth had been observed, and the current setting needed verification. The decision to prefer administrator-created environments was intended to preserve control while a formal request path was confirmed.

The meeting notes identified the existing service catalog as the place to follow up for environment creation. That is useful because governance controls work better when they connect to an established intake process rather than creating another hidden path.

No automated usage monitor or alternative document-processing service was implemented that day. The evidence supports decisions, assigned actions, and a refined control strategy.

## What moved

-

Defined administrator-generated environments as the controlled path for development and sandbox use.

-

Decided to block AI Builder credits in non-production pending governance approval and tenant configuration. #type/decision

-

Assigned usage-log analysis to identify significant consumers for targeted outreach.

-

Planned a transition path for users whose workflows require a different license or technical approach.

-

Identified the need to verify environment creation settings after unexpected growth.

-

Connected document-processing architecture with capacity and cost governance.

## The reusable pattern

Treat AI consumption like any shared platform resource.

Separate development capacity from production capacity. Require ownership and purpose at intake. Capture usage by environment, solution, action, and owner. Set thresholds that trigger review before exhaustion. Provide approved alternatives so blocking one path does not simply move the workload into an unmanaged tool.

The future state is automated capacity governance. A scheduled collector can resolve object IDs, calculate usage trends, notify owners, and route exceptions for approval. Deployment gates can reject solutions without an estimated consumption profile.

## Standing takeaways

-

Usage visibility is a prerequisite for cost control.

-

Non-production environments need limits as well as access.

-

Blocking a capability without an alternative creates shadow solutions.

-

Object identifiers must be resolved to accountable owners for remediation.

-

Document-heavy agent workflows need capacity evaluation before scale.

## Open thread

The next step is to verify the tenant settings, produce the current usage inventory, define thresholds, and compare lower-cost document-processing patterns against the agent workflow.
